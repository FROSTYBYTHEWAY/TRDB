# Практическая работа №4. Нормализация реляционной БД (все 30 вариантов)

**Тема:** Структуризация и пошаговая нормализация реляционной базы данных (0НФ → 1НФ → 2НФ → 3НФ/НФБК).

## Как читать работу

Для каждого варианта выполнены все пункты задания:

1. Анализ аномалий вставки, обновления и удаления.
2. Приведение к 1НФ (атомарность, первичный ключ).
3. Приведение к 2НФ (функциональные зависимости, частичные зависимости).
4. Приведение к 3НФ (транзитивные зависимости); для всех схем проверено, что детерминанты являются потенциальными ключами, т.е. схема также удовлетворяет НФБК.
5. DDL-скрипт для PostgreSQL. Каждый вариант создаётся в своей схеме `vNN`, поэтому весь файл можно выполнить подряд.

**Общие допущения.** Вычисляемые поля (`Итого`, `Сумма`) в таблицы не включаются, они считаются запросом. Если в задании не сказано иное, один ФИО/название считается идентифицирующим человека или объект, поэтому вводятся суррогатные ключи (`*_id`). Там, где предметная область допускает разные трактовки, допущение указано в начале варианта.

## Вариант 1. Интернет-заказы

*Эталонный вариант разобран в задании (раздел 3). Ниже краткий итог.*

**Аномалии.** Вставка: нельзя добавить товар/клиента без заказа. Обновление: смена телефона клиента требует правки всех его заказов. Удаление: удаление заказа №102 стирает товар «Клавиатура» и его цену.

**1НФ.** Ключ `(Номер_заказа, Товар)`, списки разнесены по строкам, `Итого` удалён.

**2НФ.** `Номер_заказа → Дата, Клиент`; `Товар → Цена, Категория`; `(Номер_заказа, Товар) → Кол-во`. Таблицы: `Orders`, `Products`, `Order_Items`.

**3НФ.** `order_id → client_id → (имя, телефон, город)`; `product_id → category_id → category_name`.

```sql
CREATE SCHEMA IF NOT EXISTS v01; SET search_path TO v01, public;

CREATE TABLE clients (
    client_id SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    phone VARCHAR(20) NOT NULL UNIQUE,
    city VARCHAR(60) NOT NULL
);
CREATE TABLE categories (
    category_id SERIAL PRIMARY KEY,
    category_name VARCHAR(80) NOT NULL UNIQUE
);
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    current_price NUMERIC(10,2) NOT NULL CHECK (current_price >= 0),
    category_id INT NOT NULL REFERENCES categories(category_id)
);
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    order_date DATE NOT NULL DEFAULT CURRENT_DATE,
    client_id INT NOT NULL REFERENCES clients(client_id)
);
CREATE TABLE order_items (
    order_id INT NOT NULL REFERENCES orders(order_id) ON DELETE CASCADE,
    product_id INT NOT NULL REFERENCES products(product_id),
    quantity SMALLINT NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
```

## Вариант 2. Поликлиника (приёмы)

*Допущение: у врача один основной кабинет. Списки анализов и диагнозов независимы друг от друга, поэтому уже на 1НФ выносятся в отдельные отношения (иначе их декартово произведение даёт ложные строки).*

**0НФ:** `Номер_талона, Дата, ФИО_пациента, Полис_ОМС, ФИО_врача, Специальность, Кабинет, Назначенные_анализы (список), Диагнозы (список)`

**Аномалии.**
- Вставка: нельзя завести нового врача или пациента, пока не оформлен талон.
- Обновление: смена кабинета врача требует правки всех его талонов; пропуск одной строки даёт два разных кабинета у одного врача.
- Удаление: удаление единственного талона пациента Петрова стирает сведения о нём и его полисе.

**1НФ.** Три отношения, значения атомарны:

`Talons` (PK `Номер_талона`)

| Номер_талона | Дата | ФИО_пациента | Полис_ОМС | ФИО_врача | Специальность | Кабинет |
|---|---|---|---|---|---|---|
| 5001 | 2026-11-02 | Петров П.П. | 1234567890 | Орлов А.С. | Терапевт | 101 |
| 5002 | 2026-11-03 | Сидорова А.В. | 9876543210 | Орлов А.С. | Терапевт | 101 |

`Talon_Analyses` (PK `Номер_талона, Анализ`): (5001, ОАК), (5001, Биохимия)
`Talon_Diagnoses` (PK `Номер_талона, Диагноз`): (5001, ОРВИ)

**2НФ.** Ключ `Talons` простой, частичных зависимостей нет. Таблицы связей имеют составной ключ из двух атрибутов и неключевых атрибутов не содержат, поэтому тоже во 2НФ.

**3НФ.** Транзитивные зависимости:
- `Номер_талона → ФИО_врача → Специальность, Кабинет`
- `Номер_талона → Полис_ОМС → ФИО_пациента`

Выносим `patients`, `doctors`, `specialties`, справочники `analyses`, `diagnoses`.

```sql
CREATE SCHEMA IF NOT EXISTS v02; SET search_path TO v02, public;

CREATE TABLE patients (
    patient_id SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    oms_policy VARCHAR(16) NOT NULL UNIQUE
);
CREATE TABLE specialties (
    specialty_id SERIAL PRIMARY KEY,
    specialty_name VARCHAR(80) NOT NULL UNIQUE
);
CREATE TABLE doctors (
    doctor_id SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    specialty_id INT NOT NULL REFERENCES specialties(specialty_id),
    cabinet VARCHAR(10) NOT NULL
);
CREATE TABLE appointments (
    ticket_no SERIAL PRIMARY KEY,
    visit_date DATE NOT NULL,
    patient_id INT NOT NULL REFERENCES patients(patient_id),
    doctor_id INT NOT NULL REFERENCES doctors(doctor_id)
);
CREATE TABLE analyses (
    analysis_id SERIAL PRIMARY KEY,
    analysis_name VARCHAR(100) NOT NULL UNIQUE
);
CREATE TABLE diagnoses (
    diagnosis_id SERIAL PRIMARY KEY,
    diagnosis_name VARCHAR(150) NOT NULL UNIQUE
);
CREATE TABLE appointment_analyses (
    ticket_no INT REFERENCES appointments(ticket_no) ON DELETE CASCADE,
    analysis_id INT REFERENCES analyses(analysis_id),
    PRIMARY KEY (ticket_no, analysis_id)
);
CREATE TABLE appointment_diagnoses (
    ticket_no INT REFERENCES appointments(ticket_no) ON DELETE CASCADE,
    diagnosis_id INT REFERENCES diagnoses(diagnosis_id),
    PRIMARY KEY (ticket_no, diagnosis_id)
);
```

**Аномалии.**

- Удаление: удаление единственного наряда на авто А123 стирает данные о машине и владельце.

**1НФ.** Работы и запчасти независимы, поэтому разнесены:

`Order_Works` (PK `Заказ_наряд, Работа`), `Order_Parts` (PK `Заказ_наряд, Запчасть`, Кол-во).

**2НФ.** В `Orders` ключ простой, частичных зависимостей нет; в связях неключевые атрибуты (`Кол-во`) зависят от всего ключа.

```sql
    PRIMARY KEY (order_id, part_id)
);
```

## Вариант 5. Библиотечный учёт

*Допущение: у книги несколько авторов (M:N), у книги одно издательство.*

**0НФ:** `Номер_билета, ФИО_читателя, Адрес, Книги_на_руках (ISBN, Название, Авторы через запятую), Издательство, Город_издательства, Дата_выдачи`

**Аномалии.**
- Вставка: нельзя внести новую книгу или читателя, пока книга не выдана.
- Обновление: смена города издательства требует правки всех строк с его книгами.
- Удаление: возврат и удаление записи о выдаче единственного экземпляра стирает данные о книге.

**1НФ.** Ключ `(Номер_билета, ISBN, Автор, Дата_выдачи)`; авторы разнесены по строкам:

| Номер_билета | ISBN | Автор | Дата_выдачи | ФИО | Адрес | Название | Издательство | Город_изд |
|---|---|---|---|---|---|---|---|---|
| 10 | 978-5-17-1 | Пушкин А.С. | 2026-11-01 | Миронов Т.А. | ул. Ленина 5 | Сборник | АСТ | Москва |
| 10 | 978-5-17-2 | Тургенев И.С. | 2026-11-01 | Миронов Т.А. | ул. Ленина 5 | Отцы и дети | АСТ | Москва |

**2НФ.**
- `Номер_билета → ФИО, Адрес`
- `ISBN → Название, Издательство, Город_изд`
- `Автор` входит в ключ только как связь «книга – автор»
- `(Номер_билета, ISBN) → Дата_выдачи`

**3НФ.** `ISBN → Издательство → Город_издательства`. Выделяем `publishers`; авторы в `authors` и `book_authors`; выдача в `loans`.

```sql
CREATE SCHEMA IF NOT EXISTS v05; SET search_path TO v05, public;

CREATE TABLE readers (
    ticket_no SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    address VARCHAR(200) NOT NULL
);
CREATE TABLE publishers (
    publisher_id SERIAL PRIMARY KEY,
    publisher_name VARCHAR(100) NOT NULL UNIQUE,
    city VARCHAR(60) NOT NULL
);
CREATE TABLE books (
    isbn VARCHAR(17) PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    publisher_id INT NOT NULL REFERENCES publishers(publisher_id)
);
CREATE TABLE authors (
    author_id SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL
);
CREATE TABLE book_authors (
    isbn VARCHAR(17) REFERENCES books(isbn) ON DELETE CASCADE,
    author_id INT REFERENCES authors(author_id),
    PRIMARY KEY (isbn, author_id)
);
CREATE TABLE loans (
    loan_id SERIAL PRIMARY KEY,
    ticket_no INT NOT NULL REFERENCES readers(ticket_no),
    isbn VARCHAR(17) NOT NULL REFERENCES books(isbn),
    issue_date DATE NOT NULL DEFAULT CURRENT_DATE,
    UNIQUE (ticket_no, isbn, issue_date)
);
```

```sql
CREATE SCHEMA IF NOT EXISTS v06; SET search_path TO v06, public;

    full_name VARCHAR(120) NOT NULL,

);
CREATE TABLE room_categories (
    category_id SERIAL PRIMARY KEY,
    category_name VARCHAR(50) NOT NULL UNIQUE,
    price_per_night NUMERIC(10,2) NOT NULL CHECK (price_per_night > 0)

CREATE TABLE rooms (
    room_no VARCHAR(10) PRIMARY KEY,
    category_id INT NOT NULL REFERENCES room_categories(category_id)
);
CREATE TABLE administrators (
    admin_id SERIAL PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL
);
CREATE TABLE extra_services (
    service_id SERIAL PRIMARY KEY,
    service_name VARCHAR(100) NOT NULL UNIQUE
);
CREATE TABLE bookings (
    booking_id SERIAL PRIMARY KEY,
    guest_id INT NOT NULL REFERENCES guests(guest_id),
    room_no VARCHAR(10) NOT NULL REFERENCES rooms(room_no),
    admin_id INT NOT NULL REFERENCES administrators(admin_id),
    check_in DATE NOT NULL,
    check_out DATE NOT NULL,
    CHECK (check_out > check_in)
);
CREATE TABLE booking_services (
    booking_id INT REFERENCES bookings(booking_id) ON DELETE CASCADE,
    service_id INT REFERENCES extra_services(service_id),
    PRIMARY KEY (booking_id, service_id)
);
```

## Контрольные вопросы

1. **Что такое аномалии вставки, обновления и удаления?** Побочные эффекты работы с ненормализованной таблицей: нельзя добавить данные об одной сущности без другой, изменение одного факта требует правки множества строк, удаление одной записи уничтожает данные о другой сущности.
2. **Требования 1НФ.** Все атрибуты атомарны, нет повторяющихся групп и списков, определён первичный ключ.
3. **Требования 2НФ.** Отношение в 1НФ, каждый неключевой атрибут полностью зависит от всего составного ключа (нет частичных зависимостей). Если ключ простой, отношение в 1НФ автоматически во 2НФ.
4. **Требования 3НФ.** Отношение во 2НФ и нет транзитивных зависимостей: неключевой атрибут не зависит от другого неключевого атрибута.
5. **Чем НФБК отличается от 3НФ?** В НФБК каждый детерминант функциональной зависимости должен быть потенциальным ключом. 3НФ допускает исключения, когда зависимый атрибут является частью потенциального ключа.
6. **Что такое функциональная зависимость?** `X → Y` означает, что каждому значению `X` соответствует ровно одно значение `Y`.
7. **Что такое декомпозиция без потерь?** Разбиение отношения, при котором естественное соединение полученных отношений восстанавливает исходное без лишних и потерянных строк. Обеспечивается тем, что общие атрибуты разбиения образуют ключ хотя бы одного из отношений.
8. **Зачем нужны внешние ключи?** Для обеспечения ссылочной целостности: нельзя сослаться на несуществующую запись родительской таблицы, а поведение при удалении задаётся `ON DELETE`.
9. **Зачем удалять вычисляемые поля (`Итого`)?** Они дублируют информацию, которую можно получить запросом; хранение создаёт риск рассогласования и аномалию обновления.
10. **Что такое суррогатный ключ и когда он нужен?** Искусственный идентификатор (`SERIAL`), не несущий смысла предметной области. Нужен, когда естественный ключ длинный, составной или может меняться (ФИО, телефон).
